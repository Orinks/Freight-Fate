# Rust port — implementation plan

Spec: `docs/superpowers/specs/2026-08-22-rust-port-design.md`. Reference
maps (module graph, API tables, env vars, RNG sites, test buckets) live in
the session scratchpad `map-*.md` files and are summarised where a task
needs them.

## Conventions every task follows

- Rust 2021, `rust-version = 1.85`, workspace at repo root. `cargo fmt`,
  `cargo clippy -p <crate>` clean on the files you own.
- One Python module → one Rust module of the same name under the matching
  crate; one Python test file → one Rust test module/file of the same name.
  Keep Python doc comments that explain *why* (they carry tester history).
- Spoken strings are copied byte for byte. Numbers through `pyfmt`
  (`round_py`, `round_py_n`, `fmt_money`, ...) and `units`.
- Random numbers through `ff_core::pyrandom::PyRandom` only, seeded exactly
  as the Python site seeds (int, xor'd int, or str).
- No `getattr`-style dynamism: optional attributes become `Option`, duck-typed
  hooks become trait methods with default impls.
- File ownership is disjoint per parallel task. Module declarations
  (`mod x;`) are pre-created by the lead; tasks never edit `lib.rs`,
  `Cargo.toml` or anything outside their list. Need a dep or a new module?
  Say so in the report; the lead adds it.
- Tasks never run `git`. Build with
  `CARGO_TARGET_DIR=target/<task> cargo test -p <crate> <filter>` so parallel
  tasks do not serialise on one target lock.
- A task is done when its tests pass and it returns: files written, the
  public API it exposes (signatures), anything it left stubbed, and any
  Python behaviour it could not reproduce.
