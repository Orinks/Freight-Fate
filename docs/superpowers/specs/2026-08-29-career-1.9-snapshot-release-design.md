# Career 1.9 Snapshot Release Design

## Goal

Make Career 1.9 snapshots ready for ordinary players: download, extract, and
run. Players must not set environment variables, fetch music, install native
audio libraries, or run setup scripts. Source builders get one command that
prepares dependencies and produces the same complete portable build that CI
publishes.

## Release line

Career 1.9 gets a dedicated scheduled snapshot workflow. It builds from
`feat/career-1.9` while that branch is the active release line. When Career 1.9
is merged, one explicit workflow setting changes the source branch to `dev`;
the updater contract and tag family do not change.

The existing 1.8 `nightly-*` workflow remains intact until that transition.
Career 1.9 snapshots use `1.9-tester-YYYYMMDD` tags so both release lines can
coexist without either updater selecting the other line.

## Public music pack

The approved encrypted `music.pak` is stored as a public Vercel Blob rather
than committed to Git or included in the website deployment bundle. Its stable
public entry point is:

`https://dev.orinks.net/downloads/music.pak`

The Orinks site redirects that path to the current public Blob object. This
keeps the large file out of both repositories and allows the backing object to
change without changing Freight Fate's build configuration.

The release tool carries the approved SHA-256 digest and verifies every
download before replacing a local pack. `FREIGHT_FATE_MUSIC_URL` and
`FREIGHT_FATE_MUSIC_SHA256` remain optional maintainer overrides for testing or
recovery. They are not part of the beginner instructions.

The download is written to a temporary file in the destination directory,
hashed, and atomically moved into place only after validation. An interrupted,
missing, or corrupt download cannot replace a valid local pack.

## Native audio libraries

BASS and its required add-ons remain outside Git because they are proprietary.
Freight Fate's permitted noncommercial releases continue to bundle the pinned
runtime DLLs and their license notices.

The build path automatically runs the existing BASS fetcher after dependencies
are installed. Every library must match its pinned SHA-256. A missing,
unavailable, or changed upstream binary fails the build instead of producing a
silent release. The completed Windows archive contains BASS, its required
add-ons, SDL2, Prism, and all applicable notices beside the executable in the
locations the game already loads.

## Player and builder experience

A player downloads the appropriate GitHub release archive, extracts it, and
runs `FreightFate.exe`. Music, sound, speech, data, licenses, and native
libraries are already present. The player documentation does not direct a
normal player through source setup.

Windows source builders run one repository script. It:

1. checks that Rust and `uv` are available;
2. installs the locked development and build dependencies;
3. fetches and verifies BASS;
4. downloads and verifies `music.pak` when necessary;
5. builds and smoke-tests Career 1.9; and
6. writes the complete portable archive under `dist/`.

Missing prerequisites produce short actionable messages. The script may assume
Git, Rust, and `uv` are installed; it does not install system-wide software or
request administrator privileges. The underlying release tool owns dependency
preparation after the Python environment exists, so local builds and CI follow
the same path.

## Scheduled snapshot workflow

The Career 1.9 workflow runs once daily and supports manual dispatch. Scheduled
runs publish only when curated player-facing changelog entries have appeared
since the previous Career 1.9 snapshot. The existing explicit force-build
marker permits an intentional refresh without a new changelog entry.

A successful run:

1. checks out the configured Career 1.9 source branch;
2. prepares the toolchain and locked dependencies;
3. runs the applicable Python tooling tests and Rust checks;
4. fetches and verifies the music pack and native libraries;
5. builds and smoke-tests every required release artifact;
6. generates curated notes and SHA-256 checksums; and
7. publishes a GitHub prerelease tagged `1.9-tester-YYYYMMDD` with the title
   `Freight Fate 1.9 tester snapshot YYYY-MM-DD`.

Windows is the required initial release artifact because it is the fully
supported Career 1.9 target. Other platforms may be published only after their
native build and smoke checks pass; their absence must not be disguised as a
successful supported build.

Publishing is all-or-nothing for the workflow's required artifacts. A failed
scheduled run publishes nothing and may use the existing single delayed retry
pattern. It never replaces a known-good release with incomplete files. A
manual rerun for the same UTC date may safely replace that date's prerelease
only after the entire new artifact set passes.

## Updater contract

The existing 1.9 updater behavior remains the contract. A packaged Career 1.9
build on the snapshot channel selects the newest `1.9-tester-*` prerelease and
the matching platform artifact. It ignores 1.8 `nightly-*` releases and stable
releases. The stable channel never offers a tester snapshot.

The updater downloads to a temporary location and applies only a complete,
verified artifact. Failed downloads or installation attempts leave the current
game and the portable `saves` directory untouched.

## Documentation and changelog

The README separates player instructions from contributor and release-builder
instructions. The opening download section stays player focused. Advanced
source-building details point to the one-command path and explain prerequisites
without exposing ordinary users to music URLs or manual DLL staging.

Player-facing release changes receive concise entries under `## Unreleased`.
Snapshot notes are generated from those curated entries, never raw commit
subjects. Text remains plain, screen-reader friendly, and free of decorative
formatting or maintainer-only jargon.

## Verification

Automated checks cover:

- default and overridden music URLs and hashes;
- corrupt, interrupted, and already-present music-pack behavior;
- pinned BASS fetching and missing-library failures;
- the one-command builder's prerequisite and success paths;
- required files, licenses, packs, and DLLs inside the portable archive;
- changelog-based scheduled-build decisions and release-note generation;
- workflow branch, tag, title, retry, and all-or-nothing publication rules;
- 1.9 snapshot selection and isolation from 1.8 and stable releases;
- platform asset selection and safe failed-update behavior; and
- a headless packaged smoke launch using the actual staged payload.

After deployment, the stable Orinks URL is checked for successful redirect,
expected size, and the approved SHA-256. The first published snapshot is
downloaded as a player would receive it, its checksums and archive contents are
verified, and its packaged smoke test is rerun before the release is announced.

This work does not add controls or visual UI. Accessibility review focuses on
clear screen-reader-friendly setup text, truthful spoken updater messages, and
ensuring the simplified path never requires inaccessible manual file hunting.

## Out of scope

- Installing Git, Rust, or `uv` automatically.
- Committing BASS binaries or `music.pak` to either Git repository.
- Changing the stable release channel or promoting Career 1.9 to stable.
- Reworking the updater UI beyond corrections required by this release
  contract.
- Retiring the 1.8 snapshot workflow before Career 1.9 moves to `dev`.
